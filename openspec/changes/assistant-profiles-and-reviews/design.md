## Context

本 change 建立在 `platform-foundation`（骨架与数据层）与 `eval-knowledge-base`（词条与审核后台）之上。知识库解决「怎么评」，本 change 解决「评出来是什么」：结构化的 AI 购物助手档案、可对比的评分卡，以及深度评测文章。

三者必须共用同一套评测维度体系（Totalk 评测罗盘），否则评分无依据、文章与档案无法互链、站内内容网络无法形成。

约束条件：

- MVP 不自动调用第三方 AI 助手跑分，评分由 AI 生成草稿 + 人工审核录入
- 评分具有主观性，必须靠 rubric 与证据约束
- 维度权重会迭代，必须可追溯
- 收录厂商信息需注意来源标注与合规边界

## Goals / Non-Goals

**Goals:**

- 定义评测罗盘 v0.1：维度、评分口径、权重与综合分计算、证据要求
- 交付 AI 购物助手档案页与评分卡，支持 2–4 个助手横向对比
- 交付评测文章，并与助手档案、评测维度、知识库词条互链
- 复用并扩展已有审核后台，覆盖两类新内容

**Non-Goals:**

- 自动化跑分（自动调用各 AI 助手执行 benchmark）
- 实时价格/库存抓取
- 社区讨论、用户评分与评论
- 榜单的历史快照与时间序列对比

## Decisions

### D1. 维度体系：版本化数据，而非硬编码

评测维度存于数据库（`evaluation_dimensions` 表 + `framework_version` 记录），包含维度 key、名称、定义、0–5 分各档 rubric、权重。

理由：权重与评分口径必然迭代，硬编码会导致历史评分无法解释；版本化后才能回答「这个分数是按哪套口径打出来的」。

备选：写在代码常量里——实现简单，但权重调整后旧分数失去可解释性，排除。

### D2. 评分口径：0–5 整数分 + 每档 rubric

每个维度打 0–5 的整数分，每一档都有明确的 rubric 描述（例如「3 分 = 能给出基本正确的商品，但链接有效率低于 80%」）。综合分为加权平均，保留 1 位小数。

理由：整数分 + 明确 rubric 可显著降低主观差异，也便于人工复核。

### D3. 证据强制：无证据视为未评

每个维度评分必须关联至少一条证据（评测时间、使用的 prompt、样本、观测结果）。缺证据的维度在评分卡上显示为「未评」，不参与综合分计算，并在页面上明示。

理由：这是平台可信度的核心防线——结论必须可复核。

### D4. 评测罗盘维度清单（v0.1）

| 维度 | 关注点 |
|---|---|
| 需求澄清 | 信息不足时是否主动追问 |
| 商品检索准确性 | 商品是否匹配、链接是否有效、幻觉率 |
| 价格与优惠计算 | 满减、券、到手价是否算准 |
| 时效与库存真实性 | 价格库存是否为当前真实数据 |
| 决策质量 | 推荐是否贴合需求，是否存在偏向 |
| 安全与合规 | 风险品是否警示、建议是否安全 |
| 多轮与个性化 | 是否保持上下文与偏好记忆 |
| 链路完成度 | 能否真正走到下单 |
| 引用可溯源 | 结论是否有出处 |

MVP 权重默认等权，后续按评测实践调整并留痕。

### D5. 档案数据模型：扩展表 + 独立评分表

`assistant_profiles` 作为 `content_items` 的扩展表（厂商、入口、能力范围、数据日期），`profile_scores` 存放每个维度分与证据。

理由：评分是细粒度、可增量的数据，与档案主信息分开便于按维度对比与按时间追加。

### D6. 对比视图：`/compare?ids=...`

支持任选 2–4 个助手生成维度对比表，服务端渲染输出。

理由：对比表是读者决策时最需要的形态，且必须 SSR 以保证收录与分享预览。

### D7. 评测文章：多对多关联

`review_articles` 扩展表，通过关联表绑定 `assistant_profiles` 与 `evaluation_dimensions`；正文 MDX 中引用词条时自动内联为站内链接。

理由：互链是站内内容网络的关键，也是 SEO 内链策略的基础。

### D8. 时效展示：显式数据日期

档案页与评分卡顶部展示「评测数据日期」；超过设定天数时展示时效提示。

理由：AI 助手能力迭代极快，无日期的评分会迅速失真并损害平台可信度。

### D9. 种子脚本：`scripts/seed-profiles.mjs` 与 `scripts/seed-reviews.mjs`

生成档案与文章草稿，要求每条评分附证据、每个事实附来源；无证据的维度落为「未评」。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 评分主观、被质疑不公 | 每档 rubric 明确（D2）+ 证据强制（D3）+ 公开标注评测方 |
| 厂商能力快速变化导致评分过期 | 显式数据日期与时效提示（D8） |
| 权重调整导致榜单排序突变 | 维度体系版本化留痕（D1） |
| 收录厂商名称/素材的合规风险 | 仅使用公开信息，标注来源与抓取时间，不使用未授权截图 |
| 收录范围争议（为何没有某助手） | 页面明示当前收录范围与纳入标准 |
| 横向对比被简化为「谁第一」 | 对比页强调分维度差异与适用场景，弱化单一总分排名 |

## Migration Plan

1. 新增 `evaluation_dimensions`、`framework_version`、`assistant_profiles`、`profile_scores`、`review_articles` 及相关关联表
2. 初始化 v0.1 维度体系数据（含 rubric 与等权权重）
3. 扩展 `/admin` 支持档案与文章两类内容的审核
4. 上线 `/assistants`、`/assistants/[slug]`、`/compare`、`/reviews`、`/reviews/[slug]`
5. 运行种子脚本生成草稿，人工审核后发布
6. 验证互链、sitemap 覆盖新页面、评分卡渲染

回滚：全部为新增表与新增路由；移除路由即下线页面，新增表可保留（不影响既有功能）。

4. 综合分是否需要在 MVP 展示（可能存在过度简化风险）
5. 评测数据日期的过期阈值设定为多少天
